# Tuya Bluetooth "Beacon" and "Beacon Mesh" protocols

Reverse-engineered from the Tuya **Smart Life** Android app, version 7.12.0
(build 872). The source was decompiled with JADX, and key classes were recorded
as REA evidence. The goal is enough detail to build a Linux/BlueZ controller in
this project.

Everything below comes from static analysis of the shipped app. **Nothing has
been tested against a real device yet.** Claims the code does not prove are
marked **UNVERIFIED**.

The companion file [`tuya_beacon_reference.py`](tuya_beacon_reference.py) is a
byte-exact Python reference for every frame, cipher and checksum described
here. Its built-in test vectors were generated by the app's own decompiled Java
code. Run `python3 docs/protocols/tuya_beacon_reference.py` to re-check them.

Class names below are JADX's names for the obfuscated classes, for example
`bluetooth.pbddddb`, which is `com.thingclips.sdk.bluetooth.pbddddb`.
"Thingclips" is Tuya's SDK brand. Citations use class and method names rather
than line numbers, because the names are stable within this build. A new app
release will rename everything.

## 1. Three protocols, not one

The app has **three distinct protocols** that Tuya markets under "beacon" names.
They share one trick: the payload travels as a list of 16-bit service UUIDs
(see §2). Beyond that they differ in addressing, keys and crypto.

| | Beacon v1 ("P1") | Beacon v2 ("P2") | Thing Beacon Mesh |
|---|---|---|---|
| App product family | `tbeacon`, config type 400 | `tbeacon`, config type 400 | scan type 500, `config_type_beacon_mesh` |
| Matches Tuya's public "Bluetooth Beacon Mesh" docs | partly | **yes**: groups, small XXTEA cipher | no |
| Phone → device carrier | Local Name + one 128-bit UUID | 16-bit UUID list | 16-bit UUID list, **activation only** |
| Device → phone carrier | Manufacturer data, company `0xD007` | 16-bit UUID list | 16-bit UUID list, **activation only** |
| Cipher | XXTEA (big-endian words) | XXTEA + 16-byte XOR mask | AES-128-CFB |
| Addressing | device MAC | 16-bit node IDs | SIG Mesh unicast |
| Control after pairing | P1 adverts | P2 adverts | **standard SIG Mesh over a GATT proxy (0x1828)** |
| Keys from cloud | localKey, beaconKey | localKey, beaconKey, groupKey | pairKey, then SIG NetKey/AppKey |

Tuya's developer documentation describes "Beacon Mesh" with these properties:

- Communication happens over advertising.
- Group addresses run from 0x0001 to 0x5FFF.
- Relaying goes up to 3 hops.
- It uses an "AES-128-like algorithm with fewer operations".

That description matches **Beacon v2**. The cheap AliExpress "beacon mesh" lights
and remotes are most likely P1 or P2. The newer type-500 devices only use beacons
to get *into* a SIG Mesh network.

### 1.1 Identifying a device from its advertisement

| Advert content | Family | Parser |
|---|---|---|
| Manufacturer data, company bytes `07 D0`, version bits 0, cmd 1 (three rotating segments) | P1, unpaired | `bluetooth.dqdpbpq` |
| Manufacturer data `07 D0`, other cmds | P1, paired (status or reply) | `bluetooth.dbqqppp` |
| AD 0x03, 26 bytes, `hdr & 0x80` set, `(hdr>>3)&0xF == 1`, CRC over `[hdr&0xFC]`+bytes 1..24 | P2, unpaired | `bluetooth.qpbdppq.pdqppqb` |
| AD 0x03, 26 bytes, destination bytes 3..4 = `80 00` or `80 01` | P2, paired (report) | `bluetooth.ddbbqqp` |
| AD 0x03, 26 bytes, `(hdr>>3)&0xF == 8`, CRC over bytes 0..24 unmasked | Thing Beacon Mesh, unprovisioned | `bluetooth.bqdbdbd` |
| Service 0x1828 (Mesh Proxy) | provisioned SIG Mesh node, including activated type 500 | SIG Mesh stack |

## 2. The air carrier: payload as a 16-bit UUID list

Android cannot advertise arbitrary AD types, and iOS can only advertise service
UUIDs. Tuya therefore smuggles the payload through the
**Complete List of 16-bit Service UUIDs** (AD type `0x03`).

- **Transmit encoding.** The phone splits the frame into byte pairs `[b0, b1]`.
  Each pair becomes UUID `0000b1b0-0000-1000-8000-00805F9B34FB`
  (`bluetooth.qpbqpbq.bdpdqbp(byte[])`, `bluetooth.pbqppbb.pdqppqb`).
- **On air, the bytes are verbatim.** UUID16s are serialised little-endian, so
  the frame bytes appear in order inside the AD structure.
- **Size.** A 26-byte frame is 13 UUIDs: AD length 27, `1B 03 <26 bytes>`.
  With the 3-byte Flags element that is exactly 31 bytes, the legacy maximum.
- **Duplicates and order matter.** A frame can contain the same byte pair twice.
- **Advertising parameters** (`bluetooth.qqdqbpb`, `bluetooth.bpbbpdd`):
  - legacy advertising, connectable;
  - `ADVERTISE_MODE_LOW_LATENCY` (about 100 ms), TX power HIGH;
  - each request is advertised for its "send time" (see the timing tables).
- **Two frames at once.** When the phone supports several advertising sets,
  two-frame requests go out on two sets simultaneously. Otherwise the frames
  alternate.
- **Extended advertising** is used only by Thing Beacon Mesh (§5.3).

Devices reply on the same carrier: a 26-byte AD 0x03 list in their own
advertisements.

### 2.1 Consequences for BlueZ (and for this project)

These were checked against BlueZ `master` source.

- **Transmit works through D-Bus.** `LEAdvertisement1.ServiceUUIDs` keeps order
  and duplicates:
  - `parse_service_uuids` uses `bt_ad_add_service_uuid`;
  - `queue_add_uuid` is a plain `queue_push_tail` with no de-duplication;
  - the list is serialised as AD 0x03 in insertion order.
  - The alternative is raw AD bytes through MGMT *Add Advertising*.
- **Receive does not work through D-Bus.** `Device1.ServiceUUIDs` comes from
  `device_add_eir_uuids`:
  - it **skips UUIDs already seen** (`g_slist_find_custom`);
  - it **accumulates** across adverts, so the property becomes the union of every
    frame the device ever sent;
  - frame boundaries, order and duplicates are all lost.

  The current `Bluez.Advert` reconstruction therefore cannot recover these
  frames. A raw source of LE Advertising Reports is required: the HCI monitor
  channel (as `btmon` uses) or MGMT *Device Found* events, which carry the raw
  EIR/AD bytes.
- **The passive-scan monitor may miss frames.** `Bluez.Client`'s passive
  AdvertisementMonitor matches only Flags patterns. Tuya frames that lack a
  Flags element would never be reported. Active scanning, or an extra
  `or_patterns` entry on AD type `0x03`, avoids that.
- **Each command is a short burst.** The 10 % scan duty cycle configured in
  `rootfs_overlay/etc/bluetooth/main.conf` will drop some replies. Widen the
  window while a request is outstanding.

## 3. Shared primitives

| Primitive | Definition | App source |
|---|---|---|
| CRC-8 | CRC-8/SMBUS: poly `0x07`, init `0x00`, no reflection, no xor-out. check("123456789") = `0xF4` | `bluetooth.bppqppq.bdpdqbp(byte[],int)`, `bluetooth.pbpqbbd` |
| CRC-16 | CRC-16/MODBUS: init `0xFFFF`, reflected poly `0xA001`, emitted big-endian. check = `4B 37` | `bluetooth.bppqppq.pdqppqb` |
| XXTEA | Standard XXTEA (delta `0x9E3779B9`, 6+52/n rounds) but with **big-endian** byte↔word packing. No length word. Always one 16-byte block here. | `bluetooth.bpqpqqd` (`pdqppqb` = encrypt, `bdpdqbp` = decrypt) |
| AES-CFB | `AES/CFB/NoPadding` (CFB-128) | `bluetooth.pdqppqb` |
| Key strings | A 16-char key string is used as its ASCII bytes. A 32-char one is hex-decoded. | `bluetooth.pbddddb.qqdbbpp`, `bluetooth.dqdpbpq` |
| Integers | Big-endian everywhere, except where noted | `bluetooth.dpbdbpb.bppdpdq`, `bluetooth.qbqqpbb` |

## 4. Beacon v2 ("P2")

### 4.1 Keys and addresses

| Name | What it is | Where the app gets it |
|---|---|---|
| `localKey` | Per-device, 16 ASCII chars | `DeviceBean.localKey`, set at pairing from `thing.m.device.blu.preactive` |
| `beaconKey` | Per-home "beacon mesh" key, 32 hex chars | `BeaconMeshBean.appKey` (home data), or `thing.m.device.beacon.mesh.create` |
| `groupKey` | Per-group key | `GroupBean.groupKey` |
| node ID | Device's 16-bit address | `DeviceBean.meta.beaconData.beaconNodeId`, assigned by the cloud at pre-activation |
| source ID | Phone's 16-bit address, per home | `thing.m.beacon.mesh.source.id.alloc {meshId}`, cached as `NodeId_<ownerId>` |

Address conventions:

| Address | Meaning |
|---|---|
| node ID | unicast to one device |
| `FF gg` | group with one-byte local ID `gg` |
| `FF FF` | broadcast |
| `80 00`, `80 01` | phone, as the destination of device reports |
| `0x6000`–`0x7FFF` | random source for unactivated "raw" sends |

There is **no key derivation** for normal traffic: keys are used as-is (§3).
RemoteAction, the smart-lock unlock, is the one exception (§4.8).

Which key encrypts and which masks, by destination
(`bluetooth.qqpdddb` call sites):

| Destination | XXTEA key | XOR mask |
|---|---|---|
| unicast | localKey | beaconKey |
| group | groupKey | beaconKey |
| broadcast ping | beaconKey | beaconKey |
| device → phone | beaconKey | beaconKey |

### 4.2 Frame (26 bytes, both directions)

Built in `bluetooth.pbddddb.qqdbbpp` and `pbddddb.pbbppqb`, and parsed in
`bluetooth.qpbdppq` and `bluetooth.ddbbqqp`.

| Offset | Len | Field |
|---|---|---|
| 0 | 1 | header: bit 7 = pair flag, bits 6–3 = frame type, bits 1–0 = `3` (excluded from both CRCs) |
| 1 | 2 | source address |
| 3 | 2 | destination address |
| 5 | 2 | sequence number, big-endian |
| 7 | 1 | sub-command |
| 8 | 1 | CRC-8 of the 16-byte plaintext payload |
| 9 | 16 | `XXTEA_encrypt(payload zero-padded to 16, key)` **XOR** `mask` |
| 25 | 1 | CRC-8 of `[hdr & 0xFC]` ‖ bytes 1..24, computed **before** the XOR mask |

Building a frame:

1. Pad the payload (at most 16 bytes) with zeros to 16 bytes.
2. Assemble `inner = src ‖ dst ‖ sn ‖ subCmd ‖ crc8(payload) ‖ XXTEA(payload)`.
3. Compute `crcF = crc8([hdr & 0xFC] ‖ inner)`.
4. XOR `inner[8..24)` with the mask.
5. Emit `hdr ‖ inner ‖ crcF`.

Parsing reverses this:

1. Check that the destination is `8000` or `8001`.
2. Remove the mask.
3. Check `crcF`.
4. Decrypt the payload.
5. Check the payload CRC.

The bits 1–0 that both CRCs exclude are probably a relay hop counter.
**UNVERIFIED:** the app never relays, so it never changes them.

### 4.3 Requests the app sends

| Request (class) | hdr | type | subCmd | Payload before padding | Key |
|---|---|---|---|---|---|
| Pair (`pppbpdp`) | `0x93` | pair + 2 | — | special, §4.5 | localKey |
| Reset (`dqdbdpd`) | `0x0B` | 1 | `0x01` | `02` | localKey |
| DP set, no ack (`dqdpqpq`) | `0x0B` | 1 | `0x05` | DP TLVs (§4.4) | localKey or groupKey |
| DP set, ack wanted (`pqpbpqd`) | `0x0B` | 1 | `0x06` | DP TLVs | localKey |
| Add to group (`qbqqdqq`) | `0x0B` | 1 | `0x01` | `A1 gg` | localKey |
| Remove from groups (`bqpqqbb`) | `0x0B` | 1 | `0x01` | `A2 g1 [g2 …]` | localKey |
| Ping (`dpdpqpd`) | `0x13` | 2 | `0x01` | `01` | localKey, or beaconKey for broadcast |
| Dismiss group (`qdppdpp`) | `0x13` | 2 | `0x01` | `A2 gg`, sent to `FF gg` | groupKey |
| Raw data (`ddqbbqp`) | `0x10 + n` | 2 | `0x05` | TLV with DP id `0x57` | caller key |
| Lock remote action (`dpddddp`) | `0x18` | 3 | `0x21` | 16 bytes, §4.8 | HKDF key |

Sequence numbers come from `bluetooth.dqddqdp`:

- There is one 16-bit counter per (home, source ID), persisted by the app.
- It starts at 0 and wraps at 65535.
- The sequence number is fixed when a request is queued, so every repeat of one
  request carries the same value.
- The **app** filters replayed device reports per (home, device address)
  (`bluetooth.ddbbqqp`). A report is dropped when its sequence number equals
  the last one, or is lower by at most 55 536. **UNVERIFIED:** whether devices
  apply the same rule to phone commands; reusing a sequence number should be
  assumed to fail.

### 4.4 DP encoding (P2)

Each data point is `[dpId][(dpType << 4) | len][value]`. TLVs are concatenated,
and the total must be 16 bytes or less (`bluetooth.dqdpbpq.bdpdqbp(DpsCombine)`).

| dpType | Schema | Value |
|---|---|---|
| 0 | raw | bytes |
| 1 | bool | 1 byte |
| 2 | value | 4 bytes, big-endian |
| 3 | string | UTF-8 |
| 4 | enum | 1 byte: index into the schema range |
| 5 | bitmap | big-endian integer, receive only |

For example, switch (dp 1) on and brightness (dp 3) = 500 encodes as
`01 11 01 03 24 00 00 01 F4`.

### 4.5 Pairing (activation)

Run by `bluetooth.bddqqbb` (log tag `tbeacon_config_b2Activator`).

The **unpaired advertisement** is a 26-byte AD 0x03 frame
(`bluetooth.qpbdppq.pdqppqb`):

| Offset | Len | Field |
|---|---|---|
| 0 | 1 | header with pair flag set and type 1, i.e. `0x88`–`0x8B` |
| 1 | 4 | `srand` |
| 5 | 6 | MAC |
| 11 | 8 | product ID, ASCII |
| 19 | 1 | software version, as major/minor nibbles |
| 20 | 1 | flag, must be 0 |
| 21 | 4 | `srandEncrypted` |
| 25 | 1 | CRC-8 of `[hdr & 0xFC]` ‖ bytes 1..24 |

The flow:

1. Obtain a meshId through `thing.m.device.beacon.mesh.create`. This also yields
   beaconKey.
2. Call `thing.m.device.blu.preactive`. Request:
   - `meshId`, `mac`, `pid`, `isShare=false`, `type=1`;
   - `protocolOpt`: `sv`, `flag`, `srand`, `srandEncrypted`, `beaconVer="2"`.

   Response: `beaconNodeId`, `localKey`, `beaconKey`, `relyCloud`. A set
   `relyCloud` aborts the flow.
3. Send **P2Pair** (header `0x93`). It is not masked and has no sequence number.

   | Offset | Len | Field |
   |---|---|---|
   | 0 | 1 | `0x93` |
   | 1 | 4 | MAC bytes 2..5 |
   | 5 | 1 | round number, 0–3 |
   | 6 | 2 | assigned node ID |
   | 8 | 1 | CRC-8 of beaconKey |
   | 9 | 16 | `XXTEA_encrypt(beaconKey, localKey as ASCII)` |
   | 25 | 1 | CRC-8 of `[0x90]` ‖ bytes 1..24 |

4. The device answers with a pair-flag type-3 frame. Its 4-byte `beaconExt` is
   decrypted with beaconKey.
5. Call `thing.m.device.blu.active`. Request:
   - `gid`, `mac`, `productId`, `sv`, `timeZone`, `bindUser`, `type=1`;
   - `protocolOpt`: `srand`, `beaconVer="2"`, `beaconExt`.

   The response is the devId.
6. On failure, retry in rounds 1–3. After the final round the error is `205213`.

**UNVERIFIED:** that `PreActivateResult.beaconKey` equals `BeaconMeshBean.appKey`.
Receive decryption only works if they match.

### 4.6 Device reports

Reports are decoded by `bluetooth.qpbdppq.bppdpdq`. Their destination is
`8000`/`8001`, and they are unmasked and decrypted with beaconKey.

| Pair flag | Type | subCmd | First payload byte | Meaning |
|---|---|---|---|---|
| 1 | 3 | any | | pair result: `beaconExt` = payload[0..4) |
| 0 | 1 | 2 | `01` | ping reply (**UNVERIFIED**) |
| 0 | 1 | 2 | `02` | reset acknowledged |
| 0 | 1 | 2 | `A3` | group list: payload[1..9) holds up to 8 one-byte group IDs |
| 0 | 1 | 7, 9, 10, 11 | | DP report as TLVs (§4.4). The difference between 7 and 9–11 is **UNVERIFIED** |
| 0 | 3 | `0x22` | | lock remote-action result |

Replies are matched to requests by **source address and reply type only**.
There is no echoed sequence number. The app forwards DP reports to the cloud
with `thing.m.device.dp.report`.

### 4.7 Timing

The app's defaults, in milliseconds. "Send" is how long the frame is advertised.
"Window" is how long the app listens for a reply.

| Request | Send | Window | Ack expected |
|---|---|---|---|
| DP set (`0x05`) | 3000 | 5000 | no (success assumed) |
| DP set with ack (`0x06`) | 1000 | 1000 | yes, a DP report |
| Reset | 2000 | 2000 | yes |
| Ping | 2000 | 2000 for 1 device, else 5000 | yes |
| Pair | 2000 per round | 2000 | yes |
| Group add/remove | 5000 | 5000 | yes |
| Dismiss group | 2000 | — | no |

A type-0 request (pair, reset, group) cancels queued type-2 requests (DP,
ping). Normal DP sets are not retried.

### 4.8 Smart-lock remote action

Header `0x18`, subCmd `0x21`, source `8001`, destination `0001`
(`bluetooth.dpddddp`).

The key is derived with HKDF-SHA256:

- IKM = UTF-8(`secKey` + `localKey`);
- salt = hex-decode(sha256_hex(`transactionId` + `devId`));
- info = `"SKPhone"`;
- L = 16.

The 16-byte payload is:

| Offset | Len | Field |
|---|---|---|
| 0 | 1 | `5F` |
| 1 | 1 | `0E` |
| 2 | 2 | member ID (bit 15 = admin) |
| 4 | 4 | phoneKey |
| 8 | 8 | transactionId |

The payload is encrypted with AES-128-CBC (no padding, IV = the transactionId as
ASCII), then XORed with the same key. The reply layout is in
`beacon.receiver.RemoteControlBeaconResp`.

## 5. Beacon v1 ("P1")

### 5.1 Phone → device

P1 does **not** use the 16-bit UUID list. Built by
`bluetooth.dqdpbpq.bdpdqbp(byte,String,long,byte[],String)`:

- The phone renames its Bluetooth adapter to the **first 8 characters of
  Base64(MAC)**, which goes on air as AD `0x09` Complete Local Name.
- It advertises one **128-bit service UUID** (AD `0x07`) whose 16 bytes are an
  XXTEA block. Flags + name + UUID128 = 31 bytes.
- The UUID string is built from the reversed block, so the block appears
  verbatim on air. **UNVERIFIED:** this relies on Android serialising UUID128s
  little-endian.

Plaintext block before `XXTEA_encrypt(block, key)`:

| Offset | Field |
|---|---|
| 0 | command |
| 1 | CRC-8 of the 6-byte MAC (the implicit target) |
| 2–4 | sequence number, 24-bit big-endian |
| 5–13 | payload, up to 9 bytes, zero-padded |
| 14 | CRC-8 of bytes 1..13 |
| 15 | `0x80` = first of two frames, otherwise `0x00` |

A 16-byte payload is split across two frames:

- **Frame A:** sequence number `sn`, payload bytes 0..8, flag `0x80`.
- **Frame B:** sequence number `sn+1`, payload bytes 9..15 in block bytes 5..11.
  Block byte 12 is 0 and block byte 13 is the CRC-8 of the full 16-byte payload.

| Request | Cmd | Payload | Key |
|---|---|---|---|
| Pair | 2 | beaconKey, 16 bytes over 2 frames, sequence number 0 | localKey |
| Reset | 3 | `03` | localKey |
| Ping | 3 | `02` | localKey, or beaconKey to MAC `FF…FF` |
| DP set | 7 | `dpId, dpType, len, value`: one DP, value of 6 bytes or less | localKey or groupKey |
| Add to group | 8 | `00 gg` | localKey |
| Remove / dismiss group | 8 | `01 g…` | localKey or groupKey |

- **Group target:** MAC `FF FF FF FF FF gg`.
- **Broadcast:** `FF`×6.
- **Sequence numbers:** a per-MAC counter. If the device replies "SnReply"
  (cmd 4, data[0] = 0) with its own sequence number, the phone resyncs to that
  value + 1 and retries once.

### 5.2 Device → phone

Manufacturer-specific data (AD `0xFF`) with company bytes **`07 D0`**. The AD
element fills all 31 bytes and there is no Flags element (`bluetooth.dbqqppp`):

| Offset (from the company ID) | Field |
|---|---|
| 0–1 | `07 D0` |
| 2 | bits 7–6 = version (0), bits 5–0 = command |
| 3–8 | MAC |
| 9–12 | sequence number, big-endian |
| 13–28 | `XXTEA_encrypt(plain, localKey as ASCII)` |

The decrypted block holds the sequence number (4 bytes, must equal the header
copy) followed by 10 data bytes. Replays are dropped when the sequence number is
not above the last one seen for that MAC.

| Command | data[0] | Meaning |
|---|---|---|
| 4 | 0 | SnReply: data[1..4) is the device's sequence number |
| 4 | 1, 3 | pair succeeded |
| 4 | 5 | reset acknowledged |
| 4 | 6, 7, 8 | beacon-auth event |
| 5, 6 | | DP report: `[id][type][len ≤ 7][value]` |
| 9 | 2 | group list |

### 5.3 Pairing

**Unpaired devices** advertise command 1 in three rotating segments. The
sequence-number field acts as segment index 0..2.

The flow (`bluetooth.ppqbqbb`):

1. Collect all three raw adverts.
2. Call `thing.m.device.beacon.active`. Request:
   - `encryptedData` = the 3 adverts as a JSON hex array;
   - `ability=5`, `pv="2.0"`, `bindUser`, and others.

   The response holds `devId`, `localKey`, `beaconKey` and `secKey`.
3. If `meta.beaconData.flag & 0x80` is set, the device is one-way. Pairing is
   then complete.
4. Otherwise, if `pv == "00"`, send P1Pair with beaconKey and wait for command 4
   with data[0] = 1 or 3.

## 6. Thing Beacon Mesh (scan type 500)

**Beacon frames are used only to get a device into the user's SIG Mesh
network.** After that it is an ordinary SIG Mesh node, controlled over a SIG
Mesh GATT proxy with Tuya vendor-model messages.

### 6.1 Frame types on the 16-bit UUID channel

Every frame is 26 bytes of AD 0x03, except the 50-byte extended frame. The
header is `(type << 3) | version`.

| Header | Type | Direction | Meaning |
|---|---|---|---|
| `0x40`–`0x43` | 8 | device → phone | unprovisioned advert |
| `0x48` | 9 | phone → device | activation, legacy, part 1 |
| `0x50` | 10 | phone → device | activation, legacy, part 2 |
| `0x58` | 11 | device → phone | activation response |
| `0x60` | 12 | both | recover request/response, reset request |
| `0x68` | 13 | phone → device | activation, extended advert or GATT helper, 50 bytes |
| `0x70` | 14 | phone → device | SIG proxy wake-up |

### 6.2 Unprovisioned advert (type 8)

Parsed by `bluetooth.bqdbdbd.pdqppqb`.

| Offset | Len | Field |
|---|---|---|
| 0 | 1 | header (`version = hdr & 3`) |
| 1 | 6 | MAC |
| 7 | 8 | product ID |
| 15 | 4 | deviceRand |
| 19 | 4 | auth, sent to the cloud as `encryptValue` |
| 23 | 1 | category: bit 0 = needs a publish address, bit 1 = supports recover, bit 2 = supports extended advertising |
| 24 | 1 | reserved |
| 25 | 1 | CRC-8 of bytes 0..24, header **not** masked |

### 6.3 Credentials from the cloud

The app never computes the per-device key. It sends `mac`, `deviceRandom` and
`encryptValue` (the advert's auth field) to the cloud and receives a **pairKey**:

- **Batch call:** `m.thing.device.pair.key.batch.get` v2.0. Request: `number`,
  `meshId`, `data=[{mac, deviceRandom, encryptValue}]`. Response:
  `{pairKeyBatchVOList:[{mac, pairKey, success}], nodeIds:[…]}`. The cloud
  also allocates the unicast address here.
- **Single call:** `m.thing.device.pair.key.get`.

This is Tuya's "one device, one key" licence. **Activating a new device needs
the Tuya cloud.** If deviceRand changes, the cached pairKey is invalid.

### 6.4 Activation request

The 44-byte plaintext (`beacon.core.transfer.bdpdqbp.qqdbbpp`):

| Offset | Len | Field |
|---|---|---|
| 0 | 16 | SIG NetKey |
| 16 | 16 | SIG AppKey |
| 32 | 1 | `00` (**UNVERIFIED**: probably the SIG provisioning flags) |
| 33 | 4 | IV index, big-endian |
| 37 | 2 | unicast address, big-endian |
| 39 | 2 | publish address (category bit 0), else `00 00` |
| 41 | 2 | `00 00` |
| 43 | 1 | CRC-8 of bytes 0..42 |

- **Cipher:** `AES-128-CFB(key = pairKey, IV = deviceRand ‖ 12 zero bytes)`.
- **Legacy frames:** `48 ‖ MAC[3..6) ‖ C[0..22)` and `50 ‖ MAC[3..6) ‖ C[22..44)`.
- **Extended frame** (category bit 2 and a 50-byte-capable radio), 50 bytes:
  `68 ‖ MAC(6) ‖ AES-CFB(00 ‖ bytes 0..40 ‖ CRC-8)`. That plaintext is
  43 bytes: no trailing `00 00`, and the CRC covers the leading `00`.
- **Publish address** = `localId + 0x4000`, from
  `m.thing.device.group.common.local.id.alloc` with `type=3`.

The two frames are advertised together, or alternately for 600 ms each, for
6 s in total. The app then listens for up to 8 s.

### 6.5 Activation response (type 11)

`58 ‖ MAC(6) ‖ E(18) ‖ CRC-8`. Decrypt E with the same AES-CFB key and IV
(`bluetooth.dddbppd`):

| Offset | Len | Field |
|---|---|---|
| 0 | 2 | meshCategory |
| 2 | 2 | meshCategoryExt |
| 4 | 2 | firmware major, minor |
| 6 | 2 | unicast address (must match the request) |
| 8 | 3 | netAuth |
| 11 | 2 | MCU version, packed 5/5/6 bits; 0.0.0 = none |
| 13 | 5 | unused |

The app then registers the node with `m.thing.ble.mesh.join` v3.1:

- `uuid` and `mac` = MAC;
- `nodeId` = unicast address;
- `devKey` = `""`;
- `options`: `companyId="07d0"`, `meshCategory`, `serviceLayerData.pubAddress`.

### 6.6 Recover, reset, and the GATT helper

- **Recover:**
  `60 ‖ MAC(6) ‖ 01 ‖ AES-CFB(pairKey)(nodeId(2) ‖ NID(1) ‖ 0×14 ‖ CRC-8)`.
  NID is the SIG k2 NID of the NetKey. It re-joins a device the cloud already
  knows.
- **Reset:**
  `60 ‖ MAC(6) ‖ 00 ‖ AES-CFB(pairKey)(unicast(2) ‖ netAuth(3) ‖ 0×12 ‖ CRC-8)`.
  Here `netAuth = SHA-256(lowercase hex(NetKey) + hex(AppKey))[0..3)`.
- **GATT helper:** with 5 or more devices in a batch, the app connects to one
  unprovisioned device over Tuya BLE GATT:
  - service `FD50`;
  - write characteristic `…0001-…07D0`, notify characteristic `…0002-…07D0`;
  - frame code `0x801B`, unencrypted.

  It relays the `0x68` or `0x60` frames through that device, and responses
  return as code `0x801C`. The full layout is in
  [`notes/thing_beacon_mesh.md`](notes/thing_beacon_mesh.md) §2.8.

### 6.7 Control and status after activation: standard SIG Mesh

- **Bearer:** GATT Mesh Proxy service **`0x1828`**: write to `0x2ADD` (Data
  In), notify from `0x2ADE` (Data Out), standard proxy SAR. The app has **no**
  AD 0x2A ADV-bearer transmit path.
- **Wake-up advert before connecting** (`bluetooth.bdqqqpq`), advertised for 20 s:
  `70 ‖ FF FE FF FF FF FF ‖ AES-CFB(key = NetKey, IV = AppKey)(P19)`. P19 is:
  - `00`;
  - source address (2 bytes);
  - proxy sequence number (4 bytes, big-endian);
  - `00 14`;
  - 9 zero bytes;
  - CRC-8.

  **UNVERIFIED:** whether nodes require it before accepting a proxy connection.
- **Network layer:**
  - standard SIG Mesh encryption with NetKey/AppKey (AKF = 1);
  - TTL 8;
  - one 24-bit sequence number per mesh, also used as the TID, restored with
    +1000 on reconnect;
  - the source address comes from `thing.m.sig.mesh.source.id.alloc`.
- **Tuya vendor model `0x07D0:0004`.** Opcodes are `[op | 0xC0, 0xD0, 0x07]`:

  | Opcode | Meaning | Parameters |
  |---|---|---|
  | `C9 D0 07` | DP set, acked | `01 ‖ dpRec…` |
  | `CA D0 07` | DP set, unacked | `01 ‖ dpRec…` |
  | `C8 D0 07` | DP set with TID | `tid ‖ 01 ‖ dpRec…` |
  | `CC D0 07` | DP query | |
  | `CD D0 07` | device report | `01`/`05 ‖ dpRec…` |
  | `CE D0 07` | device TID report | |

- **dpRec** = `dpId ‖ type ‖ value`. Bool, value (int32 big-endian) and enum
  carry **no length byte**. Raw, string and bitmap carry one.
- **Lights** also use SIG models: Generic OnOff `0x8202`/`0x8203`, Light
  Lightness `0x824C`, CTL Temperature `0x8264`, HSL `0x8276`.
- **Groups** need Config Model Subscription Add, which is signed with the
  DevKey. Activation registers an empty DevKey, so **UNVERIFIED:** group
  support for type-500 nodes.

## 7. What a controller needs from the Tuya cloud

None of these protocols can be bootstrapped offline. After a one-time export,
everything above runs locally.

| Family | Needed once | Needed for each new device |
|---|---|---|
| P1 | beaconKey; localKey and groupKey per device and group | `thing.m.device.beacon.active` |
| P2 | beaconKey, phone source ID; localKey, nodeId and groupKey | `blu.preactive` and `blu.active` |
| Thing Beacon Mesh | SIG NetKey, AppKey, IV index, phone source address; node unicast addresses | `pair.key.batch.get`, `ble.mesh.join` |

The keys appear in the device and home data the cloud returns: `localKey`,
`meta.beaconData`, `BeaconMeshBean`, and the SIG mesh bean.

## 8. Implications for universal_proxy

The ESPHome Native API has no message for transmitting advertisements, and Home
Assistant has no beacon integration. P1 and P2 control therefore has to run on
the device.

Additions needed in the `bluez` library:

1. **Legacy advertising with an ordered UUID16 list**, through
   `LEAdvertisingManager1.RegisterAdvertisement`:
   - the exported `LEAdvertisement1` object must allow duplicate `ServiceUUIDs`;
   - one advertisement per command, lasting the send time in §4.7;
   - P1 additionally needs `LocalName` plus one UUID128.
2. **A raw advertising-report source** that keeps each AD 0x03 list intact
   (§2.1).

For Thing Beacon Mesh:

- **Activation** needs the same advertising support and the cloud pair key.
- **Control** is SIG Mesh over a normal GATT connection. The existing active
  connection path (`UniversalProxy.ESPHome.BluetoothProxy`) can already carry
  it. The SIG Mesh and vendor-model logic would live wherever the controller
  runs.
